# Windows transport bundle

**State:** assembly, guarded preparation, update, finalization, retirement and retained-data reinstall paths are implemented in source. A genuine signed driver package, successful Windows installation/load, Code Integrity and network protection are not validated. There is no release installer. See the [Roadmap](../Roadmap.md) for acceptance tests; the operations below describe capabilities, not successful deployment evidence.

`scripts/assemble_windows_package.ps1` assembles the 26-file product administrative source set from the Qt GUI build (including the offline signature helper), the Windows SDK service build, Qt 6.8.2 MinGW64, its MinGW runtime, a separate Qt 6.8.2 MSVC Release installation, genuine Visual C++ redistributable inputs, and a supplied classifier driver package. It copies the repository's Inter fonts and creates the exact `qt.conf` expected by deployment admission.

Run it in a new PowerShell process with absolute paths on fixed local drives:

```powershell
& .\scripts\assemble_windows_package.ps1 -QtBuild <gui-build> -SdkBuild <service-build> -QtRoot <qt-mingw-root> -QtMsvcRoot <qt-msvc-release-root> -VcRedistRoot <vc-redist-x64-crt-directory> -VcNoticesRoot <vc-original-notices-directory> -MinGwRoot <mingw-root> -QtDocsRoot <qt-6.8.2-docs> -StandardLicensesRoot <standard-license-texts> -DriverPackageRoot <signed-driver-inputs> -OutputRoot <new-bundle-directory>
```

`DriverPackageRoot` must contain `GateBouncerClassifier.sys`, `GateBouncerClassifier.inf` and `GateBouncerClassifier.cat`. All three are retained and copied as original bytes to `source/driver/`. Before creating output, assembly compares the retained INF and repository INF with the exact byte length and SHA-256 identity in the repository's retained `driver/package_identity.h`. Administrative admission compiles that same identity and compares bytes read from the original INF handle before catalog verification, both for source and staged files. A differently signed INF, changed service, destination or startup directive is rejected. Changing the INF requires updating this version's identity and obtaining a catalog for those unchanged final bytes; line endings are part of that identity. Assembly does not generate a catalog, sign files, download tools or verify signing. The standalone driver build produces an unsigned SYS and is insufficient for product admission. `-Laboratory` explicitly selects the separate 23-file laboratory input set and rejects `DriverPackageRoot`; a missing product driver never selects that mode automatically.

The output parent must exist. The output directory must be new and separate from every input. Each output is created relative to its retained original parent handle using a single filename and a create-only disposition. Missing files, reparse points, existing outputs, changed retained identities, or a failed write/readback stop assembly with exit code 2. Partial output is preserved after a failure; it must not be distributed.

The notice input set is explicit: 49 original Qt Core/GUI attribution pages, the three module index pages, and `qtdoc/licensing.html`, `licenses-used-in-qt.html` and `qtentrypoint.html` from the installed Qt 6.8.2 documentation. The original HTML bytes are copied; documentation assets and relative navigation are not included. The script also copies Qt's installed `sbom/qtbase-6.8.2.spdx.json`, GCC license and runtime exception texts, the winpthreads license, and the repository's Inter license. The supplied standard license directory must contain `LGPL-3.0-only.txt`, `GPL-3.0-only.txt`, `GPL-2.0-only.txt` and `Qt-GPL-exception-1.0.txt`. These are labeled as standard license texts and are not represented as Qt 6.8.2 source. All 68 notice files must exist; the script does not download or fabricate missing materials. These materials do not identify every compiled third-party component or certify all redistribution requirements; applicable source, attribution, relinking and documentation redistribution obligations still require a distribution review.

`QtMsvcRoot/bin/Qt6Core.dll` is copied to `source/service-msvc/Qt6Core.dll`, separate from the GUI's root MinGW QtCore. `VcRedistRoot` must supply the original amd64 `msvcp140.dll`, `msvcp140_1.dll`, `vcruntime140.dll` and `vcruntime140_1.dll` from licensed Visual C++ redistributable material; they are copied to the application root for the service's eager `/MD` imports. Installed System32 files are rejected as runtime inputs. The redistributable version must support the actual service compiler toolset. `VcNoticesRoot` supplies the original `Redist.txt` and `ThirdPartyNotices.txt`; the MSVC Qt installation supplies its separate qtbase SBOM. These three additional notice files bring the required notice set to 68. The materials are retained and copied without asserting complete redistribution rights or license compliance. Distribution authentication and applicable licenses remain requirements.

The service resolves its eager imports using ApplicationDir and System32, and delays QtCore until its original deployment, service registration and product driver admission are current. It rejects preloaded CRT modules from another directory and a preloaded QtCore. The delay-load hook uses only the separately admitted MSVC module. Actual module paths and image mappings are checked against original retained package files under the administrative filesystem/Windows-loader trust boundary; this does not establish a FileID for a mapped image, Code Integrity or traffic protection. The modules and original deployment handles remain retained for the process lifetime, including the parser's static destructors. Debug Qt is not substituted for the Release input.

The closed legacy 21-file product and 18-file laboratory inventories remain admissible for original maintenance and ordinary readers. New staging requires 26 or 23 respectively. A legacy inventory cannot load the new service parser without its five runtime originals; no missing runtime selects another Qt installation or a PATH search.

The resulting directories have different purposes:

- `source/` contains exactly the 26 product input files (or 23 with explicit `-Laboratory`), without a deployment manifest or license extras.
- `notices/` contains the supplied license materials.
- `BUNDLE.txt` identifies the output as a transport bundle.

Administrative preparation computes and writes its own deployment inventory from retained source files. This assembler does not create a deployment manifest.

The service has a separate product preparation entry, `--prepare-deployment <source> <new-package> <new-store> <account-SID>`. It requires an elevated administrator running the original service image from an authenticated administrative source directory: the exact 26-file set, retained original files and directories, protected administrative ACLs, and no reparse points. Before creating administrative roots or staging files, admission verifies the original SYS and INF as SHA-256 catalog members under Windows' offline `DRIVER_ACTION_VERIFY` policy. The signed CTL is decoded from the retained CAT's bytes; the verifier supplies the original member handles and does not reopen a catalog by path. It requests cached revocation checks, disables MD2/MD4 and rejects unavailable trust or any failed member verification. The staged package repeats this verification. This is an offline driver-policy check, not a check that Code Integrity loaded that image or a promise that every attestation package satisfies the policy. The transport bundle alone does not satisfy these prerequisites. Applying an ACL or calculating a hash does not establish the provenance of an external binary; distribution authentication remains a separate requirement.

Product preparation acquires its administrative lease and original source before creating a fresh protected `HKLM\SOFTWARE\LGA\GateBouncer` root. The `LGA` parent must be protected and must not be a registry link; it is created with administrative ACLs if absent, while an existing unprotected parent is rejected. An existing product root, package or store is rejected. It stages the original files, writes and reads back its own inventory and complete configuration, creates the `LGAGateBouncer` service disabled, and only publishes automatic startup after those checks. It does not start the service. Product service dispatch uses `--service` and admits the retained deployment, configuration, SCM image, PID and product service SID. It does not use `EnableWfp` as authorization. Explicit `--prepare-guest-deployment` and `--service --guest-wfp` retain the separate laboratory gate and service identity.

Product maintenance uses `--update-deployment <current> <source> <new-package>`, `--finalize-deployment <current>` and `--uninstall-deployment <current>`. These reuse the original maintenance owners and state readbacks. Finalization accepts only the complete durable prepared tuple with a stopped service and zero PID, and finishes disabled-to-automatic startup without starting it. Failures preserve partial objects and recovery state; preparation does not adopt a partial or existing deployment. Uninstallation retains package and store data and does not unload a driver.

After `UninstalledRetained`, retain the original package and store. To reinstall in that same protected product namespace, use the existing update entry: `--update-deployment <retained-original-package> <authenticated-source> <new-package>`. It admits the original terminal retirement receipt, package identities, inventory, store, account SID and complete driver absence. It records a replacement plan, recreates only the original stopped user service with disabled startup, and resumes the existing signed-driver installation and update phases. It preserves the retirement witness through interrupted service security/SID setup and tuple writes; partial or foreign values and a different service configuration are rejected. Only confirmed new driver registration, original policy readback and automatic startup permit receipt cleanup. That policy readback accepts either the exact retained inventory or its complete absence; it never recreates filters. A completed tuple and original new-driver registration allow finalization to repeat that readback after a crash during receipt cleanup. A retained principal snapshot whose filters were removed still requires protection recovery; preparing the new installation does not reapply that snapshot. This does not prove loaded-image identity, Code Integrity or network protection.

Keep both package directories until completion. Once the replacement plan is durable, repeat the same update command to resume; after a switch, the new package is also an admitted current argument. If creation was interrupted before any replacement identity was durably recorded, that partial destination is preserved and rejected for adoption: choose another fresh package destination while keeping the original terminal package and receipt. A completed new tuple can also finish its receipt cleanup through `--finalize-deployment <new-package>`. No command automatically reboots, starts the user service or treats a retained empty registry container as an installation.

The product input set includes the driver files, but **a verified transport package is not an installed driver, and package verification does not admit protection**. The preparation source connects guarded Windows Driver Store installation to its retained authenticated INF/SYS/CAT inputs, administrative lease and protected deployment roots. It retains and verifies the distinct original Driver Store outputs and exact kernel-service configuration before completing the prepared tuple and automatic user-service startup mode. It does not start the user service. `driver/GateBouncerClassifier.inf` defines the primitive amd64 package for Windows 10 version 1903 and later, with Driver Store destination `%13%`, fixed `LGAGateBouncerClassifier` kernel service, demand startup and administrative security. Its version identifies a development package. The unchanged final INF/SYS require a genuine signed catalog; there is no unsigned or test-certificate fallback. Source implementation and offline trust do not demonstrate a successful Windows installation, loaded-image identity, Code Integrity or network protection.

The lifecycle source uses the documented primitive-driver [installation/removal APIs](https://learn.microsoft.com/en-us/windows-hardware/drivers/develop/creating-a-primitive-driver), including [`SetupCopyOEMInfW`](https://learn.microsoft.com/en-us/windows/win32/api/setupapi/nf-setupapi-setupcopyoeminfw) and [`DiInstallDriverW`](https://learn.microsoft.com/en-us/windows/win32/api/newdev/nf-newdev-diinstalldriverw). These APIs reopen paths; retained input/output identities and administrative filesystem custody bound that operation under trusted SYSTEM, Administrators and TrustedInstaller installation actors. This trust boundary never exempts their traffic from policy. Update and retirement retain original receipts through uncertain effects, service/tuple transitions and manual restart recovery; no command automatically reboots. After service startup, persistent Always rules can be reapplied only from the original protected OwnedStore, current deployment and matching retained file witnesses, with complete WFP absence checked inside the write transaction and actual readback before admitting the source. Present exact catalogs are read and validated; partial/foreign catalogs, legacy rules without witnesses, changed files and conditional rules require review. Once, process-instance and duration outcomes are not resurrected. Refusing source admission does not remove a preexisting Allow filter or prove effective blocking. These paths still require Windows execution validation; the assembler itself only assembles files.

The classifier lifetime has no unload callback, and documented partial-start/removal cases require a reboot. Without an admitted product device, the existing net-event producer can expose only its supported fallback: process-instance, Once, duration and complete protection are not established by a running service or available net events. Preparation, startup mode and transport assembly do not certify network protection.

Keep the notices with the bundle. A future installer must deliver them separately from the closed application inventory. This script does not grant administrative ACLs, create a laboratory gate, install or start a service, register login startup, sign binaries, install a driver, or establish network protection. A transport bundle is not an installed deployment.
