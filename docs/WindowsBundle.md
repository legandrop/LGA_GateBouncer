# Windows transport bundle

`scripts/assemble_windows_package.ps1` assembles the 21-file product administrative source set from the Qt GUI build (including the offline signature helper), the Windows SDK service build, Qt 6.8.2 MinGW64, its MinGW runtime, and a supplied classifier driver package. It copies the repository's Inter fonts and creates the exact `qt.conf` expected by deployment admission.

Run it in a new PowerShell process with absolute paths on fixed local drives:

```powershell
& .\scripts\assemble_windows_package.ps1 -QtBuild <gui-build> -SdkBuild <service-build> -QtRoot <qt-mingw-root> -MinGwRoot <mingw-root> -QtDocsRoot <qt-6.8.2-docs> -StandardLicensesRoot <standard-license-texts> -DriverPackageRoot <signed-driver-inputs> -OutputRoot <new-bundle-directory>
```

`DriverPackageRoot` must contain `GateBouncerClassifier.sys`, `GateBouncerClassifier.inf` and `GateBouncerClassifier.cat`. All three are retained and copied as original bytes to `source/driver/`. Before creating output, assembly compares the retained INF and repository INF with the exact byte length and SHA-256 identity in the repository's retained `driver/package_identity.h`. Administrative admission compiles that same identity and compares bytes read from the original INF handle before catalog verification, both for source and staged files. A differently signed INF, changed service, destination or startup directive is rejected. Changing the INF requires updating this version's identity and obtaining a catalog for those unchanged final bytes; line endings are part of that identity. Assembly does not generate a catalog, sign files, download tools or verify signing. The standalone driver build produces an unsigned SYS and is insufficient for product admission. `-Laboratory` explicitly selects the separate 18-file laboratory input set and rejects `DriverPackageRoot`; a missing product driver never selects that mode automatically.

The output parent must exist. The output directory must be new and separate from every input. Each output is created relative to its retained original parent handle using a single filename and a create-only disposition. Missing files, reparse points, existing outputs, changed retained identities, or a failed write/readback stop assembly with exit code 2. Partial output is preserved after a failure; it must not be distributed.

The notice input set is explicit: 49 original Qt Core/GUI attribution pages, the three module index pages, and `qtdoc/licensing.html`, `licenses-used-in-qt.html` and `qtentrypoint.html` from the installed Qt 6.8.2 documentation. The original HTML bytes are copied; documentation assets and relative navigation are not included. The script also copies Qt's installed `sbom/qtbase-6.8.2.spdx.json`, GCC license and runtime exception texts, the winpthreads license, and the repository's Inter license. The supplied standard license directory must contain `LGPL-3.0-only.txt`, `GPL-3.0-only.txt`, `GPL-2.0-only.txt` and `Qt-GPL-exception-1.0.txt`. These are labeled as standard license texts and are not represented as Qt 6.8.2 source. All 65 notice files must exist; the script does not download or fabricate missing materials. These materials do not identify every compiled third-party component or certify all redistribution requirements; applicable source, attribution, relinking and documentation redistribution obligations still require a distribution review.

The resulting directories have different purposes:

- `source/` contains exactly the 21 product input files (or 18 with explicit `-Laboratory`), without a deployment manifest or license extras.
- `notices/` contains the supplied license materials.
- `BUNDLE.txt` identifies the output as a transport bundle.

Administrative preparation computes and writes its own deployment inventory from retained source files. This assembler does not create a deployment manifest.

The service has a separate product preparation entry, `--prepare-deployment <source> <new-package> <new-store> <account-SID>`. It requires an elevated administrator running the original service image from an authenticated administrative source directory: the exact 21-file set, retained original files and directories, protected administrative ACLs, and no reparse points. Before creating administrative roots or staging files, admission verifies the original SYS and INF as SHA-256 catalog members under Windows' offline `DRIVER_ACTION_VERIFY` policy. The signed CTL is decoded from the retained CAT's bytes; the verifier supplies the original member handles and does not reopen a catalog by path. It requests cached revocation checks, disables MD2/MD4 and rejects unavailable trust or any failed member verification. The staged package repeats this verification. This is an offline driver-policy check, not a check that Code Integrity loaded that image or a promise that every attestation package satisfies the policy. The transport bundle alone does not satisfy these prerequisites. Applying an ACL or calculating a hash does not establish the provenance of an external binary; distribution authentication remains a separate requirement.

Product preparation acquires its administrative lease and original source before creating a fresh protected `HKLM\SOFTWARE\LGA\GateBouncer` root. The `LGA` parent must be protected and must not be a registry link; it is created with administrative ACLs if absent, while an existing unprotected parent is rejected. An existing product root, package or store is rejected. It stages the original files, writes and reads back its own inventory and complete configuration, creates the `LGAGateBouncer` service disabled, and only publishes automatic startup after those checks. It does not start the service. Product service dispatch uses `--service` and admits the retained deployment, configuration, SCM image, PID and product service SID. It does not use `EnableWfp` as authorization. Explicit `--prepare-guest-deployment` and `--service --guest-wfp` retain the separate laboratory gate and service identity.

Product maintenance uses `--update-deployment <current> <source> <new-package>`, `--finalize-deployment <current>` and `--uninstall-deployment <current>`. These reuse the original maintenance owners and state readbacks. Finalization accepts only the complete durable prepared tuple with a stopped service and zero PID, and finishes disabled-to-automatic startup without starting it. Failures preserve partial objects and recovery state; preparation does not adopt a partial or existing deployment. Uninstallation retains package and store data and does not unload a driver.

The product input set now includes the driver files, but **a verified package is not an installed driver, and protection is not admitted by package verification**. A successful preparation exit stages the inputs and prepares the user service; it does not complete product installation, install a driver catalog, create or start the kernel service, or establish protection. `driver/GateBouncerClassifier.inf` supplies a primitive amd64 package definition for Windows 10 version 1903 and later: Driver Store destination `%13%`, fixed kernel service `LGAGateBouncerClassifier`, demand startup, and administrative service security. Its package version is a development package identifier, not a released product version. Signing the final unchanged INF and SYS and supplying a genuine catalog remain external distribution requirements; there is no test-certificate or unsigned fallback.

The next executable installation boundary is the Windows primitive-driver lifecycle. [Microsoft recommends `DiInstallDriver`/`DiUninstallDriver` for primitive drivers](https://learn.microsoft.com/en-us/windows-hardware/drivers/develop/creating-a-primitive-driver). [`SetupCopyOEMInfW`](https://learn.microsoft.com/en-us/windows/win32/api/setupapi/nf-setupapi-setupcopyoeminfw) identifies a published INF by output path, while [`DiInstallDriverW`](https://learn.microsoft.com/en-us/windows/win32/api/newdev/nf-newdev-diinstalldriverw) accepts an INF path and returns installation/reboot status. Neither accepts retained INF/SYS/CAT input handles. A before/after identity check does not prevent either operation from resolving a changed parent between those checks. The current preparation code therefore does not connect that path-based effect or claim original Driver Store continuity. A completed entry must retain the actual Driver Store files and their distinct identities, bind them to the same deployment registration and kernel-service configuration, and account for uncertain installation and reboot state. It must also distinguish actual loaded-image/Code Integrity admission from offline catalog trust. Those operations are pending.

The classifier lifetime has no unload callback, and documented partial-start/removal cases require a reboot. Without an admitted product device, the existing net-event producer can expose only its supported fallback: process-instance, Once, duration and complete protection are not established by a running service or available net events. Preparation, startup mode and transport assembly do not certify network protection.

Keep the notices with the bundle. A future installer must deliver them separately from the closed application inventory. This script does not grant administrative ACLs, create a laboratory gate, install or start a service, register login startup, sign binaries, install a driver, or establish network protection. A transport bundle is not an installed deployment.
